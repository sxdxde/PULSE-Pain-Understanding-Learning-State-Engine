# PULSE — Pain, Understanding & Learning State Engine

PULSE is a research project that asks: *what if a reinforcement learning agent had skin?* Rather than treating danger as a number that fires once and disappears, PULSE gives the agent a **persistent, spatial, time-varying internal state** that accumulates damage from harmful experiences, fades slowly over time, and generates a growing sense of dread around known danger zones. The agent learns not just *"trap X exists"* but *"I have been hurt there before, and it is getting worse."* Phase 6 benchmarks whether this embodied pain system makes the agent converge faster and avoid danger more reliably than standard RL algorithms without it.

---

## The Core Idea

Standard RL reward signals are **stateless** — they fire on entry to a bad state and leave no trace. The agent rediscovers danger from scratch each episode. PULSE instead maintains a **Slab** (a grid of learnable vectors representing skin) that accumulates deformation every time the agent is hurt. The L2 norm of each cell's vector is its pain score. Around each trap, a **ResistanceField** adds jelly-like viscosity that the agent feels before entering. A **PainShapedPolicy** reads both layers at evaluation time and vetoes any action whose target cell exceeds an aversion threshold — the agent refuses to enter states it has learned to dread. Phase 6 measures whether this changes learning outcomes.

### Phase 1 — The World

Builds the 8×8 gridworld and trains a baseline PPO agent on it.

```bash
python train_phase1.py       # trains PPO for 50,000 steps, saves to models/
python visualise_phase1.py   # renders the trained agent's path as a PNG
```

**What to expect:** The agent learns to navigate from `(0,0)` to `(7,7)` while avoiding traps at `(3,3)`, `(4,5)`, `(2,6)`. The visualiser shows a path figure saved to `models/`.

---

### Phase 2 — The Skin (Vector Slab)

Introduces the Slab: a `(8,8,16)` PyTorch parameter grid representing the agent's skin. No training required — this phase is a demonstration.

```bash
python visualise_slab.py     # simulates trap hits, renders pain heatmap before/after healing
```

**What to expect:** Two heatmaps: one showing accumulated pain at trap cells, one after elastic recovery. Demonstrates `deform()`, `elastic_recovery()`, and `reset_cell()`.

---

### Phase 3 & 4 — Coupling and Resistance

Phase 3 wires the Slab into the live training loop (trap entries now deform the slab in real time; pain score adds a growing bonus penalty). Phase 4 adds a ResistanceField — jelly viscosity around danger zones that makes the agent pay a cost even before entering a trap.

These phases are embedded in `pulse_env.py` (marked `### PHASE 3 ###` and `### PHASE 4 ###`). They activate automatically when `PulseGridWorld` is instantiated — no separate script to run.

```bash
python visualise_resistance.py   # renders the static resistance field topology
```

**What to expect:** A blue-to-red heatmap showing `0.1` (baseline) across safe cells and `0.7` at trap cells and all their 8-neighbourhood cells. This is the "pre-entry danger gradient."

---

### Phase 5 — Pre-Entry Aversion

Trains a PPO agent (same as Phase 1) and evaluates it with `PainShapedPolicy` — an evaluation-time filter that vetoes actions whose target cells exceed an aversion threshold (`depth × resistance > 0.5`).

```bash
python train_phase5.py           # trains PPO, then runs 20 PULSE-filtered eval episodes
python visualise_aversion.py     # 10 eval episodes with step-by-step console diagnostics
python compare_phase5.py         # 50 vanilla vs 50 PULSE episodes, saves comparison PNG
```

**What to expect:** `visualise_aversion.py` prints a table of aversion scores for all 4 directions at every step and draws blocked actions as faded red arrows on the episode path. `compare_phase5.py` saves a 3-panel comparison figure.

---

### Phase 6 — Convergence Benchmark

The full experiment: three agents, five seeds, metrics recorded every 1,000 steps.

```bash
python benchmark.py          # runs ~15 training runs, saves benchmark_results.csv
                             # estimated time: 15–40 minutes on CPU
python plot_benchmark.py     # generates benchmark_results.png (4-panel figure)
python results_summary.py    # prints text summary with convergence times + interpretation
```

**What to expect:** See *How to Read the Benchmark Results* below.

## How to Read the Benchmark Results

### The Four Panels

`benchmark_results.png` shows four panels. Here is how to interpret each:

**Panel 1 — Reward over time**
The primary learning signal. All three agents are trained to maximise this. A faster-rising curve means faster convergence. Wide shaded bands mean the algorithm is sensitive to random seed — its outcome is unreliable. Narrow bands mean it is stable. *Caveat: reward alone is ambiguous. A higher reward could come from goal-reaching, trap-avoidance, or shorter paths — three distinct mechanisms. Read alongside Panels 2 and 3.*

**Panel 2 — Trap entry rate over time**
The PULSE-specific test. This measures exactly what the aversion filter targets: how often does the agent walk into a trap? A downward trend means the agent is learning (or being filtered) away from danger. If PULSE-PPO's trap rate drops faster than vanilla PPO's, the aversion filter is doing its job. If it doesn't, the shaped reward from Phase 3–4 already achieves the same effect without the filter — a meaningful finding either way.

**Panel 3 — Goal reach rate over time**
The primary task metric. An agent that avoids all traps but never reaches the goal is safe but useless. An agent that reaches the goal every episode but does so by luck (passing near traps) is competent but fragile. Both panels 2 and 3 must improve simultaneously for PULSE to be declared genuinely beneficial. The dashed line at 80% marks the convergence threshold used in `results_summary.py`.

**Panel 4 — Episode length over time**
Efficiency. Shorter episodes mean the agent finds the goal faster (14 steps is optimal). *Caution: trap-terminated episodes are also short (1–5 steps if the trap is near the start). A very low episode length in early training almost certainly means many trap hits, not good navigation. Read alongside Panel 2 to disambiguate.*

### The Shaded Bands

Each band spans mean ± 1 standard deviation across the 5 seeds. A wide band means the algorithm's performance varies strongly between seeds — your specific result depends heavily on the random initialisation. A narrow band means the algorithm is reliable: it will perform similarly regardless of the seed.

If two agents' bands overlap substantially, the observed difference in means may be noise. If the bands are separated, the difference is likely real (though N=5 is not enough for formal significance testing — see below).

### Statistical Caveats

The benchmark uses **N=5 seeds**. This is standard in RL research for preliminary demonstrations. It is **not** sufficient for formal hypothesis testing (p-values with N=5 have high Type I and II error rates). `results_summary.py` reports **Cohen's d** instead — an effect size that gives directional evidence about the magnitude of any difference. Interpret as:

| d value | Meaning |
|---------|---------|
| \|d\| < 0.2 | Negligible — likely noise |
| 0.2–0.5 | Small — worth noting |
| 0.5–0.8 | Medium — suggests a real effect |
| > 0.8 | Large — strong evidence the difference is real |

For publication-strength claims, use N ≥ 20 seeds.

### If PULSE Doesn't Win

A negative result is not a failure — it is information. `results_summary.py` prints a detailed interpretation for each possible outcome:

- **PULSE better on both metrics** → the mechanism works; test on harder environments
- **PULSE lower trap rate but not faster convergence** → filter helps safety but adds path-cost overhead; try a lower threshold
- **PULSE faster convergence but not lower trap rate** → faster goal-reaching but not via the aversion mechanism; investigate path choices
- **PULSE worse on all metrics** → the filter may be over-active on this environment; try a higher threshold (0.8+) or delayed activation

The most likely explanation for a PULSE underperformance in Phase 6 is that the Phase 3–4 shaped reward (resistance costs + pain bonus penalties) already guides vanilla PPO away from traps well enough that the eval-time filter adds no incremental benefit. This would be a meaningful finding: it would suggest the reward shaping, not the aversion filter, is the load-bearing contribution of the PULSE design.

## Key Design Decisions

**Why a Vector Slab (not a scalar pain counter)?**
A 16-dimensional vector per cell can encode multiple pain "channels" simultaneously — direction, intensity, recency. The L2 norm collapses these to a single pain score but preserves the richer internal representation for future gradient-based training.

**Why resistance × depth for aversion (not just depth)?**
The product requires *both* pain memory (the agent has been hurt there) *and* physical danger (the cell is in a known risk zone). Depth alone would flag frequently-traversed safe cells; resistance alone would flag trap neighbours the agent has never experienced. The product is an AND gate: confirmed personal suffering in a physically dangerous location.

**Why apply the filter at evaluation, not training?**
Applying it at training time would violate PPO's on-policy assumption (the filter changes which actions are taken, but PPO's gradient assumes the policy generated the data). This would produce biased experience, non-stationary value estimates, and conflated credit assignment. The filter is a *deployment-time guard*, not a training mechanism. Keeping them separate makes each component independently interpretable.

**Why 5 seeds?**
A single RL training run is one sample from a distribution of possible outcomes. A single run cannot distinguish algorithm quality from random luck. Five seeds is the minimum for directional evidence in published RL research; twenty or more is needed for statistical significance.
